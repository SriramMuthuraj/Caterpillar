# Smart Rental Tracking - Anomaly Detection Module

This module provides an end-to-end data pipeline and verification dashboard designed to detect operational anomalies, telemetry inconsistencies, and behavioral deviations in the Caterpillar Smart Rental Tracking system.

It is structured in a clean, decoupled, and modular fashion to make it straightforward for team members and AI agents to integrate into the parent application.

## ⚙️ How the Anomaly Detection Pipeline Works

The anomaly detection engine uses a **3-Tier Analysis architecture** to evaluate rentals. It executes sequentially, ensuring that lower-level data issues do not corrupt higher-level statistical analysis.

```
                  ┌────────────────────────┐
                  │   Raw Telemetry CSV    │
                  └───────────┬────────────┘
                              │
                              ▼
            ┌───────────────────────────────────┐
            │   Tier 1: validate.py (Gate)      │
            └─────────┬───────────────────┬─────┘
                      │                   │
             (If fails validation)  (If passes validation)
                      │                   │
                      ▼                   ▼
            ┌───────────────────┐ ┌───────────────────────────────────┐
            │   Integrity Flags │ │      Tier 1: asset_rules.py       │
            │   (3 points each) │ │          (2 points each)          │
            └───────────────────┘ ├───────────────────────────────────┤
                                  │     Tier 2: self_baseline.py      │
                                  │          (3 points each)          │
                                  ├───────────────────────────────────┤
                                  │     Tier 2: group_analysis.py     │
                                  │          (3 points each)          │
                                  └───────────────┬───────────────────┘
                                                  │
                                                  ▼
                                  ┌───────────────────────────────────┐
                                  │     Tier 3: severity.py           │
                                  │   (Combines & computes scores)    │
                                  └───────────────┬───────────────────┘
                                                  │
                                                  ▼
                                  ┌───────────────────────────────────┐
                                  │     (Optional) explain.py         │
                                  │  (Generates plain-text summaries)  │
                                  └───────────────┬───────────────────┘
                                                  │
                                                  ▼
                                  ┌───────────────────────────────────┐
                                  │    Output JSON/CSV Reports & UI   │
                                  └───────────────────────────────────┘
```

### Pipeline Steps

1. **Step 1: Data Integrity Check ([validate.py](file:///e:/projects/caterpillar/anomaly-detection/src/validate.py))**
   - **Gatekeeper Pattern**: Checks the raw records for basic errors. If a row fails any validation check, it is marked as **invalid** and is **dropped** from the dataset used to calculate peer group averages and historical baselines. This prevents faulty records from skewing normal ranges.
2. **Step 2: Business Logic Validation ([asset_rules.py](file:///e:/projects/caterpillar/anomaly-detection/src/asset_rules.py))**
   - Applies static, logic-based thresholds to each valid record individually (e.g. checks if active rentals are overdue, if operators are assigned, or if the asset was severely under-utilized).
3. **Step 3: Self-Baseline Comparison ([self_baseline.py](file:///e:/projects/caterpillar/anomaly-detection/src/self_baseline.py))**
   - Compares the current rental's daily engine hours with the specific machine's historical averages. It calculates the statistical deviation to flag abnormal usage behavior.
4. **Step 4: Cohort Comparison ([group_analysis.py](file:///e:/projects/caterpillar/anomaly-detection/src/group_analysis.py))**
   - Compares the machine's daily idle ratio against three cohort dimensions: **Equipment Type**, **Site ID**, and **Last Operator ID**. Outliers that deviate significantly from cohort averages are flagged.
5. **Step 5: Score & Severity Mapping ([severity.py](file:///e:/projects/caterpillar/anomaly-detection/src/severity.py))**
   - Merges all flags triggered on a single record. It sums their relative weights to compute a composite score and maps it to a severity band:
     - **Critical** (Score $\ge 6$)
     - **Warning** (Score $\ge 3$)
     - **Normal** (Score $< 3$)
6. **Step 6: Plain-Language Explanations ([explain.py](file:///e:/projects/caterpillar/anomaly-detection/src/explain.py))**
   - If enabled and an API key is present, calls Gemini to convert the raw numerical flags into a clear, single-sentence summary for a fleet manager.

## 🔍 Detail of Modules & Mathematical Rules

### 1. Data Integrity Layer ([validate.py](file:///e:/projects/caterpillar/anomaly-detection/src/validate.py))
- **Impossible Hours**: Fired if `Engine_Hours_Day + Idle_Hours_Day > 24.0`. *(Weight: 3)*
- **Bad Date Order**: Fired if `Check_Out_Date < Check_In_Date`. *(Weight: 3)*
- **Zero-Activity Row**: Fired if `Engine_Hours_Day == 0.0` and `Idle_Hours_Day == 0.0`. *(Weight: 3)*
- **Rental Days Mismatch**: Fired if the absolute difference between `Rental_Days` and actual elapsed days between `Check_In_Date` and `Check_Out_Date` is non-zero. *(Weight: 3)*
- **Booking Conflict**: Checks if the same `Equipment_ID` has overlapping rental date intervals. Active rentals without check-out dates use a simulated current date (default `2025-06-15`). *(Weight: 3)*

### 2. Basic Asset Rules ([asset_rules.py](file:///e:/projects/caterpillar/anomaly-detection/src/asset_rules.py))
- **Unassigned Equipment**: Fired if `Site_ID` is literal `"NULL"` or empty. *(Weight: 2)*
- **No Accountability**: Fired if `Last_Operator_ID` is literal `"NULL"` or empty. *(Weight: 2)*
- **Under-Utilization**: Fired if `Idle_Hours_Day / (Engine_Hours_Day + Idle_Hours_Day) > 0.75`. *(Weight: 2)*
- **Overdue active rentals**: Fired if a rental is active (no `Check_Out_Date` value) and has been active for more than `20` days relative to the simulated current date. *(Weight: 2)*

### 3. Self-Baseline Analysis ([self_baseline.py](file:///e:/projects/caterpillar/anomaly-detection/src/self_baseline.py))
- Analyzes historical rows for the same `Equipment_ID` where the `Check_In_Date` is chronologically prior to the current record.
- **Mathematical Formula**:
  $$\mu = \text{mean}(X_{\text{hist}}), \quad \sigma = \text{std}(X_{\text{hist}}, \text{ddof}=1)$$
  $$\text{Deviation Score} = \frac{|X_{\text{curr}} - \mu|}{\max(\sigma, 10^{-6})}$$
- Fired if $\text{Deviation Score} > 2.0$. *(Weight: 3)*

### 4. Group Imbalance Cohorts ([group_analysis.py](file:///e:/projects/caterpillar/anomaly-detection/src/group_analysis.py))
- Compares a record's daily idle ratio ($IR$) with the cohort average.
- **Mathematical Formula**:
  $$\text{Cohort Average } (\mu_{\text{cohort}}) = \frac{1}{N} \sum_{i \in \text{cohort}} IR_i$$
  $$\text{Deviation} = |IR_{\text{curr}} - \mu_{\text{cohort}}|$$
- Fired if $\text{Deviation} > 0.20$ (20 percentage points difference). *(Weight: 3)*

## 🛠️ Edge Cases Handled

The module includes several safeguards to prevent noise and division-by-zero crashes:
1. **Low Sample Cohorts**: If a Type, Site, or Operator group has fewer than 3 valid members, the group analysis is skipped for those records to avoid false alarms.
2. **Zero-Variance history**: If a machine's engine hours are perfectly identical in historical records ($\sigma = 0$), the standard deviation is set to `1e-6` to avoid division-by-zero crashes.
3. **Missing Checkout Dates**: Active rentals are processed using a consistent `SIMULATED_CURRENT_DATE = 2025-06-15` to compute overdue statuses and overlap conflicts.
4. ** rental_days = 0**: Division operations on daily averages use `max(eng + idl, 1.0)` or safe dates logic to prevent division-by-zero exceptions.
5. **Averaging Pollution prevention**: Valid rows that fail Tier 1 validation (integrity check) are completely skipped when calculating cohort averages or self-baselines.
6. **Multi-flag Aggregation**: When multiple anomalies match the same row, flags are joined and weights are summed rather than generating duplicate alerts for the same row.

## 🚀 Integration Guide for Team Members and AI

If you are integrating this module into a larger application (e.g. backend api, scheduled data pipeline, or React/Next.js dashboard), follow these specifications.

### 1. Data Schema Requirements
The input data source (CSV or pandas DataFrame) must supply the following columns:
| Column Name | Type | Description |
|---|---|---|
| `Equipment_ID` | string | Unique asset identifier (e.g., `EQX1001`) |
| `Type` | string | Asset classification type (e.g., `Excavator`) |
| `Site_ID` | string | Site identifier, or `"NULL"` if unassigned |
| `Check_In_Date` | string | Start of rental date in `YYYY-MM-DD` |
| `Check_Out_Date` | string | End of rental date in `YYYY-MM-DD`, or `"NULL"` if active |
| `Engine_Hours_Day` | float / string | Average engine hours per day |
| `Idle_Hours_Day` | float / string | Average idle hours per day |
| `Rental_Days` | integer / string | Stated duration of rental in days |
| `Last_Operator_ID` | string | Operator identifier, or `"NULL"` if unassigned |

### 2. Python Code Integration
You can invoke the pipeline programmatically in other Python scripts as follows:

```python
import sys
import os

# Append anomaly-detection directory to path
sys.path.append("/path/to/caterpillar/anomaly-detection")

from main import run_pipeline

# 1. Run the pipeline (processes rules, self-baselines, and groups)
# This writes output/flagged_anomalies.json and output/flagged_anomalies.csv
results = run_pipeline(
    csv_path="/path/to/rental_data.csv",
    enable_gemini=False,  # Set True to fetch LLM summaries
    gemini_key=None       # Supply key if enable_gemini=True
)

# 2. Inspect results programmatically
for row in results:
    row_idx = row["row_index"]  # 1-based index (matching CSV line)
    score = row["score"]
    severity = row["level"]     # "Critical", "Warning", "Normal"
    flags = row["flags"]        # List of detailed trigger payloads
    
    if severity == "Critical":
        print(f"Alert! Row {row_idx} ({row['Equipment_ID']}) is Critical. Score: {score}")
        for flag in flags:
            print(f"  - Fired: {flag['rule']} - Details: {flag}")
```

### 3. CLI Batch Pipeline Integration
To run the module as a CLI batch process (for instance, inside a Cron job, CI script, or Airflow operator):

```bash

```
